Optional Support Listing Guide

How to offer bounded help for the MIT-licensed Session Cost Skills without gating, relicensing, or misrepresenting the public software.

Repository version: 0.2.0 · Updated 2026-09-25

1. Sell a service, not a license change

The Cline and MCode skills remain public MIT-licensed software. Anyone may use the features already in the repository without paying. A marketplace listing may sell time-based installation help, compatibility troubleshooting, confirmed-bug triage, migration guidance, or a separately scoped sponsored change.

Keep the boundary explicit. Payment covers only the service named at checkout. It does not relicense, rebrand, or remove rights from the MIT source, and it must not unlock a feature already available in the public repository.

Every customer artifact must include the unmodified root MIT LICENSE. Do not replace it with single-user, non-commercial, or commercial code terms.

2. Listing identity and copy

A truthful title pattern is:

Voluntary support for Session Cost Skills (MIT-licensed)

A concise description can say:

Optional help for the public MIT-licensed Session Cost Skills.

This purchase is for the support service described below, not for a
commercial software license. The source remains available under MIT.

Possible help includes installation, command usage, compatibility triage,
and guidance for a reproducible issue. No private credential, database,
or session transcript is required.

State the software version or “current public version” policy, supported operating systems, service window, response target, channel, and exclusions. Avoid “guaranteed,” “risk-free,” or permanent-update claims unless separately reviewed and operationally supportable.

3. Define service scope

Typical bounded services

  • Verify the Node/Bun runtime and exact Cline or MCode install path.
  • Reproduce a command with a synthetic or redacted data set.
  • Explain Cline account authentication or MCode rate refresh behavior.
  • Diagnose a confirmed bug and record a minimal redacted reproduction.
  • Deliver an agreed migration plan or small sponsored change.

Publish exclusions when applicable

  • Recovering deleted or inaccessible user data.
  • Reverse engineering a runtime or unrelated third-party system.
  • Custom provider integrations outside the stated support period.
  • Work on private repositories or data not needed for the request.
  • Any promise that public MIT features become unlocked after purchase.

A response target is not a guaranteed resolution time. Legal/business terms should define cancellation, delivery, refunds, taxes, and any service guarantee before publication.

4. Privacy and diagnostic requests

Do not ask for credentials or complete runtime data. Request the minimum needed:

  • adapter and installed/repository version;
  • operating system plus Node or Bun version;
  • the exact command with values/IDs redacted;
  • expected and actual result;
  • a short error excerpt or synthetic fixture.

Never request providers.json, secrets.json, environment dumps, SQLite ledgers, runtime JSON/JSONL, private dashboards, or account identifiers. If a user shares sensitive material, stop processing it, ask for a redacted replacement, and follow the repository’s security exposure procedure.

Explain that Cline --account uses the Cline API and MCode --refresh-rates uses provider pricing pages and atomically rewrites the installed MCode rate file only after all sources validate. The support operator should not collect those credentials.

5. Fulfillment

  1. Point the buyer to the public repository and the exact software version covered.
  2. Provide the customer support pack and the two exact install destinations.
  3. Confirm the service window, response channel, and bounded request intake.
  4. Deliver agreed guidance or a patch contribution under the repository contribution terms.
  5. Record completion without uploading a raw repository checkout, worktree, or unfiltered archive.

If software is attached to a listing, use only the allowlisted release archives defined in the release contract. Do not upload a developer checkout.

6. Pre-publication checklist

  • The listing clearly says the code is MIT-licensed and the purchase is for services.
  • The listing does not call the software paid-only or present a separate commercial code license.
  • Price, service period, response target, delivery method, exclusions, cancellation, and refund terms are current and reviewed.
  • The support email or public issue route is monitored.
  • The buyer can install from the exact session-cost paths and has the Node.js/Bun requirements.
  • Network/write disclosures for Cline account mode and MCode rate refresh are visible.
  • A test purchase, delivery, support, and refund/cancellation flow has been completed where applicable.
  • No credentials, databases, transcripts, reports, private worktree files, or unfiltered archives are attached.

7. Project support remains public

Ordinary non-sensitive project questions belong in the public issue tracker. Security reports use the private advisory route in SECURITY.md. A paid listing supplements this route; it does not make the repository less usable.
